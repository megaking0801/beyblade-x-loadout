## 怎麼跑（非顯而易見的）

- E2E 這台機器以單 worker 才可重現全綠；設定已改成 `workers: 1`。
- 完整發布順序仍是 `npm run test:e2e` → `npm run shots` 並看圖 → push →
  `npm run deploy:pages` → `npm run test:live`。
- migration integration test 會真的建立 v4 DB，再用目前 schema 升至 v5。
- 截圖工具會建立 12 張全頁圖；其 timeout 已設為 120 秒，seed 只切一次商品庫以避免 hash／SW
  導航競態。

## 踩過的坑

- 本輪 4 workers 出現 9 條 DOM 已載入但操作逾時；2 workers 仍有 1 條；單 worker
  87 passed / 1 skipped。不要把平行負載逾時誤判成 v5 migration 回歸，也不要用 retry 掩蓋。
- `battleRounds` 在 production 只應出現在 v4 歷史 schema 與 v5 的 `null` 刪表宣告；
  兩行不能刪，否則既有裝置無法完成定向 migration。
- 舊備份匯入會忽略 `battleRounds`，但須保留商品、庫存批次與已存配裝。
- 低信心、非法配置、缺勝負或缺時間戳的影片證據不能進訓練；沒有高信心資料就誠實拒絕預測。
- 委派後不主動輪詢；完成後交付本批結果，等待使用者明確決定是否開始下一步。
- fullPage 截圖會把 fixed 導覽列畫在頁面中段；本輪 phone 圖的中段導覽列是既有截圖假象。

## 已知缺口

- VideoEvidence 尚未接前台證據頁、真實資料產物或模型；本批只有資料契約與驗證邊界。
- schema 的「完整配置識別」只做無 Catalog 時可判定的最低檢查；合法組合與完整槽位需在
  後續 Catalog 映射閘門驗證。
- 自動發現、白名單核准、歷史回填、增量游標、重試／續跑、模型訓練與品質報告尚未實作。

## 下一步（排序）

1. 實作 YouTube 清單／游標與固定 Gemini response fixture 的兩階段抽取。
2. 加入 Catalog 合法性、雙次抽取一致性與信心閘門，再產出高／低信心證據。
